# Hearts upload recovery

Journey hearts upload when a level completes, when the app starts, when it
regains network connectivity, when it resumes, and when the player opens or
refreshes the hearts leaderboard. Only one queue drain runs at a time.
A successful reconnect refreshes the Home pending count, current completion
card, and an open hearts leaderboard.

Completed levels are saved with their replay before upload. Network and
profile connection failures keep the entry pending and retain an explanation.
The leaderboard displays that explanation rather than only saying that some
levels are waiting. A successful retry clears the error. JSON reloads restore
the shared reference between a completion card and its queue entry so the
card follows the retry result.

Unsupported generation versions remain queued for the existing same-UTC-day
retry window. The server must support the puzzle version generated by the
installed app. The health endpoint reports its journeyHearts capability.
Do not reset the player profile, delete device saves, fabricate submissions,
or credit an already-counted level to recover uploads.

As before, a level counts once per profile and pending completions must sync
before the UTC day changes. Expired submissions cannot be credited to a
later date by retrying. This fix does not backfill earlier days.

## Deployment race

Terraform planning listens for completion of either CI or CodeQL. Each plan
still checks that both workflows passed on the exact current main commit.
Thus an early completion can fail closed while the later completion retries
planning. Apply remains a separate manual dispatch behind the production
review environment. No safety check is removed.

## November 6 investigation

The reported Android symptom was hearts awaiting upload. The production
health endpoint reported journey-v3 while current source supports v4. The
latest automatic Terraform run had failed because CodeQL had not finished;
its subsequent success did not trigger a new plan under the old workflow.

Separate regressions reproduced missing reconnect retries and a stale
completion-card reference after JSON reload. These are fixed in source.
A production backend update and a later app build are distinct rollout
steps. Do not claim the installed phone is fixed until it has successfully
synced a new same-day completion. Ads remain parked pending k-ID.

## Confirmed server timeout follow-up

After the client retry fix and backend v4 deployment, CloudWatch showed
repeated Lambda platform timeouts at exactly 10,000 ms. API Gateway returned
503 at the same boundary, while board reads completed normally. Some completions were credited while later uploads remained queued; none
were manually credited or removed. No DynamoDB throttle/conflict datapoints were reported in the
investigated window. Puzzle replay is the likely compute bottleneck.

Terraform now allocates 2048 MB to the ARM Lambda (CPU is proportional to
memory) and aligns deadlines: Lambda 12 seconds, gateway 14 seconds, installed
app 15 seconds. Infrastructure tests require at least one vCPU-equivalent
allocation and server deadlines below the client deadline. Allocation changes
affect compute billing; faster CPU-bound execution can offset the higher
GB-second rate, but production timings must be measured.

Replay start/completion logs contain request ID, generation, level and
duration only. They exclude tokens, player IDs, seeds, marks and solutions.
These logs distinguish regeneration time from subsequent database work if a
slow request recurs. No APK change is required for this backend update.
Approve/apply the reviewed Terraform plan, then retry existing same-day
queued uploads and confirm their actual success before calling the issue
resolved. Normal UTC expiry and duplicate-level safeguards remain in place.
